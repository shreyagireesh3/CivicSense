# CivicSense 2.0

> **⚠ Prototype disclaimer:** CivicSense is a working prototype of a reusable civic intelligence and grievance-management platform. It does not connect to live BBMP systems. All analytics data is pre-computed from a provided CSV export. The Service Desk stores complaints in a local SQLite file (`data/desk.db`). This is not a production deployment.

CivicSense transforms civic grievance data into structured analytical intelligence — category concentration, ward-level demand patterns, operational status tracking, forecasting, a full Service Desk for complaint lifecycle management, and **dynamic analytics switching** when a new dataset is imported via the Data Hub.

---

## Architecture Overview

```
notebooks/              Python analytics pipeline — runs once, produces static JSON artifacts
backend/main.py         FastAPI — serves pre-computed JSON + Service Desk API + Data Hub API
backend/desk.py         Service Desk router — SQLite-backed (data/desk.db); Data Hub + analytics
dashboard/src/App.jsx   Single-file React SPA — all components in one file
data/desk.db            Live operational database (auto-created, persists all citizen complaints)
data/loaded_dataset.json  Cache of the most recently imported external dataset (auto-managed)
```

### Two Separate Data Streams

CivicSense keeps **analytics data** and **operational ticket data** strictly separate:

| Stream | Source | What it powers |
|--------|--------|----------------|
| **Analytics (historical)** | BBMP 2025 demo dataset (static JSON files generated by notebooks) — **or** an imported CSV loaded via the Data Hub | Command Centre, Analytics, Insights, Forecasts panels |
| **Operational (live)** | Every ticket submitted through the Citizen Portal — stored in `data/desk.db` tickets table | Officer Console, Citizen tracking, Data Hub exports |
| **Imported records** | Compatible external CSVs loaded via Load Dataset — stored in `imported_records` table | Dynamic analytics override (replaces the static BBMP 2025 data) |

> The `imported_records` table and the `tickets` table are completely separate. Data Hub stats/exports count only `tickets`. The analytics endpoint (`/api/desk/hub/analytics`) reads only from `imported_records`.

## Dynamic Analytics

When a CSV is successfully imported via **Load Dataset**, the dashboard automatically switches to using the imported data for all analytics panels:

1. On page load, the frontend fetches `/api/desk/hub/loaded-dataset` to check whether an imported dataset exists.
2. If one exists with records, it also fetches `/api/desk/hub/analytics` which computes live aggregations from the `imported_records` table.
3. The analytics data (categories, wards, statuses, monthly, metrics) is replaced dashboard-wide with the imported dataset values.
4. A **data source badge** appears in the Command Centre (near the KPI grid) and in the Analytics section heading, showing: `Imported dataset · <tag> · N records · date range`.
5. The sidebar footer updates to reflect the active dataset and date range.
6. To revert to the BBMP 2025 demo data, delete the loaded dataset: `DELETE /api/desk/hub/loaded-dataset`.

## Features

### Citizen Portal
- Submit a grievance (category, subcategory, ward, description) → auto-assigned ticket ID
- Track any ticket by ID to see status, officer remarks, and progress timeline
- Every submission is stored in `data/desk.db` immediately

### Officer Console
- View, filter, and update all submitted complaints
- Add status updates and officer remarks
- Citizen tracking reflects updates in real time

### Data Hub (Officer Console → Data Hub tab)
- Live record counts: total, today, this week, latest record date
- CSV export: Today / This Week / This Month / All Records / Custom date range
- Exports use the standardised CivicSense schema (8 columns)
- Shows currently loaded external dataset summary

### Load Dataset — Import Wizard (Officer Console → Load Dataset tab)
1. Upload a compatible civic grievance CSV (up to 50 MB)
2. System auto-detects column mapping via name aliases; manual override for mismatched names
3. Preview a full dataset profile: record counts, categories, wards, date range, status distribution, missing values
4. Import valid records; duplicates skipped by default; invalid rows reported with specific error messages
5. On success, analytics dashboard immediately switches to the imported dataset

### Dynamic Analytics Refresh
- `GET /api/desk/hub/analytics` — computes live aggregations from `imported_records` for the latest dataset tag
- Returns categories, wards, statuses, monthly buckets, and metrics in the same shape as the static BBMP 2025 endpoints
- Frontend checks for an imported dataset on every page load and applies it automatically if present
- `data_source` field in the response indicates `"imported"` or `"bbmp_2025"` so the UI always knows which stream is active

### Forecast Safety
- `GET /api/desk/hub/forecast-readiness` — checks whether the loaded dataset has ≥ 90 days of chronological history
- If insufficient: `"Forecast unavailable: insufficient chronological history."`
- The existing BBMP 2025 forecast panel always shows regardless of loaded dataset status

## Forecasting

The forecast uses `HistGradientBoostingRegressor` trained on daily BBMP 2025 data.

**Important:** Forecasts are **planning signals, not guarantees**. The current model has a negative R² on the test set, meaning it does not fully explain underlying variance. The 10.6% MAE improvement over the 7-day seasonal naive baseline is meaningful but limited.

**Forecast safety rule:** If a loaded dataset has fewer than 90 days of chronological coverage, the system will not attempt to generate forecasts and will clearly say so. Do not invent predictions.

## Security

- CORS: allows all origins (`*`). Restrict `allow_origins` in `backend/main.py` for production deployment.
- No authentication. The API serves civic statistics and complaint records. Suitable for a prototype / internal tool context only.
- No PII beyond what citizens voluntarily submit in complaint descriptions.
- File upload size limit: 50 MB per CSV.

---

## Limitations and Known Constraints

1. **Forecasts use BBMP 2025 data only.** The forecast dashboard uses the 2025 BBMP pipeline output. Importing a new dataset does NOT automatically retrain the forecast model — that requires re-running the Python pipeline on the new data.

2. **Dynamic analytics does not recompute drill-down views.** When an imported dataset is active, the Command Centre, Analytics (category selector), Insights sections use the imported data for top-level aggregations. The per-category drill-down charts (subcategories, category×ward, category×month, category×status) still show the BBMP 2025 static data because that requires the full Python pipeline.

3. **No authentication.** The Service Desk has no login system. Anyone with backend access can submit or modify tickets.

4. **Forecast dates are static.** The forecast dashboard JSON contains dates from the last pipeline run. Re-run `notebooks/05_forecast_dashboard_data.py` to update them.

5. **Single-file frontend.** All React components are in `dashboard/src/App.jsx` by design. This is an intentional architectural choice for this project.

6. **No real BBMP integration.** CivicSense processes a provided CSV export. It does not connect to any live BBMP system or public API.
